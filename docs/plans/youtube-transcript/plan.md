# Plan: youtube-transcript MCP plugin (v1, stdio-only)

## Context & Decision

Build the `youtube-transcript` Claude Code plugin — a stdlib-only Python MCP server that fetches existing YouTube subtitles (manual or auto-generated) via the InnerTube API, per `docs/specs/2026-08-01-youtube-transcript.md`. The spec is settled after a `research` pass with empirical verification and three `multiexpert-review` cycles, whose remaining findings the user resolved by narrowing v1 to stdio transport only. This plan is about **how** to build exactly what the spec decided.

**This plan has been through three `multiexpert-review` cycles.** Cycle 1 found and fixed a structural provider-port gap and two empirically-verified security defects (a DOCTYPE guard mechanism that does not exist on any Python version, and a missing URL-scheme check that let `file://`/`data:` URLs through). Cycle 2 found that two of cycle 1's own fixes did not actually work (the `MIN_ATTEMPT_TIMEOUT` retry-budget fix was mathematically unreachable at the stated constants; `HTTP_TIMEOUT` was being treated as a per-attempt wall-clock bound when it is a per-socket-operation timeout a slow-drip upstream can bypass), plus a self-contradictory `ALLOWED_EDGES` table, a cursor field-count contradiction, and an unreachable "fast-reject" mechanism. **Cycle 3 — the final automated cycle per the engine's 3-cycle cap — found the deadline arithmetic wrong a third time** (the "corrected" model from cycle 2 only closed by silently truncating leg 3's retry allowance by 10.25s and mischaracterizing that truncation as "the arithmetic closes"; the slow-drip check's worst-case overshoot of ~2s was unaccounted for), **plus two new instances of the exact `ALLOWED_EDGES` gap cycle 2 thought it had closed** (`providers/innertube.py` needs `formats.MAX_SEGMENTS`; `protocol/envelope.build()` needs symbols from `formats/` and `providers/base.py` it cannot reach), **plus a security-critical regression introduced by cycle 2's own `NoTranscript` redesign** (it silently dropped the spec's positive `playabilityStatus == "OK"` gate, making age-gated/login-walled/private videos fail open to `no_transcript` instead of a proper error), **plus a confirmed bypass of the new AST-based import-boundary enforcement**. Per the engine's protocol, cycle 3's FAIL was escalated to the user rather than fixed a fourth time automatically. The user's resolution, given directly: the deadline/timeout precision this area had been chasing for three cycles is not actually load-bearing for a personal-use, stdio-only v1 — **raise the time budget with generous margin instead of re-deriving tight arithmetic a fourth time** — plus fix the (non-timing) architecture and security findings directly, since each carried a concrete, specific suggested fix from its reviewer. This revision does both: the sections below show the widened deadline model and every other cycle-3 fix, applied as one manually-scoped pass per the user's direction (see Verification & Sources for how this pass relates to the formal 3-cycle limit).

### The deadline/timeout model, widened per the user's direction

Four named constants, **`HTTP_TIMEOUT = 15` now declared in `domain/` (cycle 8 — see the symbol-placement section below), the other three still in `net/client.py`**: `HTTP_TIMEOUT = 15` (seconds — the socket-level timeout passed to each connect/recv operation; `net/client.py` re-exports it from `domain/`), `HTTP_MAX_ATTEMPTS = 2` (one retry per leg), `MIN_ATTEMPT_TIMEOUT = 5`. `CPU_PHASE_BUDGET = 20` (seconds — the CPU-phase allowance itself, sized against the worst realistic CPU-phase invocation, see below) and **`ENCODE_RESERVE = HTTP_TIMEOUT + CPU_PHASE_BUDGET = 35` (cycle 7 fix — `ENCODE_RESERVE` is now derived, not chosen independently; both components importable directly within `domain/` as of cycle 8's `HTTP_TIMEOUT` relocation)** are carved out of `TOOL_CALL_DEADLINE = 180` (raised from `45s`) for the CPU phase and its slow-drip reservation together. **Network budget** = `deadline.remaining() - ENCODE_RESERVE = 145s`, computed fresh at every check point inside `net/client.py`.

**Why `ENCODE_RESERVE` is derived, not chosen (cycle 7 finding, performance review):** the prior revision picked `ENCODE_RESERVE = 20s` independently, then the slow-drip paragraph below separately required `p95(CPU) + HTTP_TIMEOUT ≤ ENCODE_RESERVE` — a self-contradiction, since that formula leaves only `20 - 15 = 5s` of actual CPU headroom while the same constant's own stated rationale (below) sizes it against a CPU-phase invocation expected to need up to `20s`. Naming `CPU_PHASE_BUDGET = 20s` as the CPU allowance on its own, and defining `ENCODE_RESERVE = HTTP_TIMEOUT + CPU_PHASE_BUDGET`, makes the two reservations additive instead of competing for the same headroom — T-16's gate 3 now checks `p95(CPU phase) ≤ CPU_PHASE_BUDGET` directly (see below), the constant it was always meant to be checked against. **Cycle 8 found the derivation as first stated wasn't constructible in code**: `ENCODE_RESERVE` lives in `domain/`, whose `ALLOWED_EDGES` row is `nothing` — it cannot import `net/client.py`'s `HTTP_TIMEOUT`. Fixed by moving `HTTP_TIMEOUT` itself into `domain/` (see the symbol-placement rule section below), so the derivation is computed where both its inputs already live.

Three review cycles were spent almost entirely on making a `45s` total budget close exactly, and each cycle's "fix" produced a new arithmetic defect in the same area — cycle 3's finding (the retry budget over-subscribed by `10.25s`, closed only by silently deleting leg 3's retry) is the clearest evidence this budget was simply too tight for the retry/backoff/CPU-phase model this design needs. v1 is a personal-use, stdio-only local tool, not a latency-bound service — trading a larger `TOOL_CALL_DEADLINE` for an unambiguous safety margin is strictly preferable to a fourth round of precision arithmetic in the same tight window.

**Pre-attempt floor — one formula, stated once** (cycle 3 found the prior draft stated three non-equivalent versions of this rule across the rule text, the worked example, and the Risks table, and that T-6b's test asserted a fourth): applied before **every** attempt, `remaining_after_backoff = network_budget_remaining - (backoff_delay if this is a retry else 0)`; if `remaining_after_backoff < MIN_ATTEMPT_TIMEOUT`, no attempt is made — raise `TransportFailed` immediately. `backoff_delay` for the single retry this design allows (`HTTP_MAX_ATTEMPTS = 2`, so there is never more than one retry per leg, which removes the 0-vs-1-indexing ambiguity cycle 3 also flagged) is `1.0 + jitter(0, 0.25)`, i.e. at most `1.25s` — this is the one and only place a backoff sleep enters the calculation.

**Clamp** — the timeout passed to each attempt is `min(HTTP_TIMEOUT, remaining_after_backoff)` — **backoff-inclusive, matching the floor formula above** (the prior draft computed the clamp from the bare `network_budget_remaining`, not `remaining_after_backoff`). **Worked example, corrected cycle 6** (the previous numeric example was itself arithmetically inconsistent under every reading — flagged in cycle 5, not actually edited until now): take `network_budget_remaining = 15s` immediately before a retry attempt. The old (bare) clamp: `min(HTTP_TIMEOUT, network_budget_remaining) = min(15, 15) = 15s`. The new (backoff-inclusive) clamp: `remaining_after_backoff = 15 - 1.25 = 13.75s`, so `min(HTTP_TIMEOUT, remaining_after_backoff) = min(15, 13.75) = 13.75s`. The old clamp would have passed the full `15s` to `socket.settimeout` while only `13.75s` of network budget actually remained — an overrun of exactly `1.25s`, i.e. `max_backoff`, with no test able to catch it under the old formula, since the one test exercising the clamp only asserted that it *doesn't* engage in the nominal case. **At these constants, and under the nominal "one blocking operation per attempt" model below, the clamp doesn't engage in the re-derived worst case** — `remaining_after_backoff` never drops below `HTTP_TIMEOUT` for any leg in that model, so the clamp always evaluates to `HTTP_TIMEOUT` itself there. **The clamp and floor remain real, load-bearing safety mechanisms, not merely defensive backstops** (cycle 8 correction — performance review found the prior wording here overclaimed precision the nominal model doesn't actually have, see the honest restatement below the worked derivation): a real attempt can involve more than one blocking socket operation, and when it does, the clamp is exactly the mechanism that keeps a single slow attempt from consuming more than its fair share of what's left.

**Re-derived worst case, nominal model** (3 legs, each needing its one allowed retry, maximal jitter, **one blocking socket operation per attempt** — see the honest scope note immediately below for why this last assumption is a simplification, not a proof): network budget = `180 - 35 = 145s`.
- Each leg, fully retried: `HTTP_TIMEOUT + backoff_delay + HTTP_TIMEOUT = 15 + 1.25 + 15 = 31.25s`.
- Three legs, all fully retried (the nominal-model maximal case — no leg's clamp or floor engages under this simplified model: after two fully-retried legs, `network_budget_remaining = 145 - 2×31.25 = 82.5s`, still far above `HTTP_TIMEOUT = 15s`): total `93.75s`.
- **Margin, nominal model: `145 - 93.75 = 51.25s`.** Unlike the prior two revisions, this nominal case is not truncated to fit and no test needs to assert a boundary case at `~6.5s` — the property that failed three times running at the old constants. **This margin is a nominal-case estimate, not a proven bound — see below.**

**Honest scope note on the nominal model, cycle 8 (performance finding):** the worst-case derivation above treats one attempt as costing exactly one `HTTP_TIMEOUT` interval. This is a simplification, not a guarantee — an HTTPS request attempt actually involves several distinct blocking socket operations (`connect`, TLS handshake, `recv` of the status line and headers, `recv` of body chunks), and the plan's own "Slow-drip defense" section a few paragraphs below independently documents this same phase measured empirically at up to `7.5 × HTTP_TIMEOUT`. Each of those operations is still individually bounded by `HTTP_TIMEOUT` at the socket level (this is what the clamp and floor above actually enforce, and why they remain load-bearing rather than merely defensive), so the realistic (non-adversarial) worst case is bounded by a modest multiple of `HTTP_TIMEOUT`, not unbounded — but it is not proven to fit within the `51.25s` nominal margin, and no test in this plan currently exercises more than one blocking operation per mocked attempt (T-6b's and T-14's mock transports model an attempt as a single clock-advance, i.e. the nominal `k=1` case only). **Accepted for v1 as sufficient without further precision-chasing on paper**: `TOOL_CALL_DEADLINE = 180s` already carries substantial headroom over the historical `45s` budget, this is a personal-use stdio tool rather than a latency-bound service, and the actual per-attempt operation count is exactly the kind of number that's cheap to *measure* (T-P3 already records per-leg TLS-handshake-vs-TTFB timing) and expensive to *derive precisely on paper* — precision-chasing this specific number across more review cycles is the pattern that already cost three cycles once (cycles 1-3) and is not worth repeating a second time for a number T-P3's real measurements will settle empirically once the plugin exists. Revisit only if real usage or T-P3's data shows the margin is actually being exhausted.

**Slow-drip defense — what it actually bounds, stated honestly after cycle 4 found the cycle-3 "residual absorbed by margin" framing was quantitatively wrong, twice over.** `HTTP_TIMEOUT` bounds each individual blocking socket operation (`connect`, one `recv`), not the sum of several within one attempt. The streaming read loop enforcing `HTTP_MAX_RESPONSE_BYTES` checks the network-budget deadline on every chunk, so the **response body** — the largest attacker-influenced surface, since it's the caption content itself — is wall-clock bounded: worst-case overshoot there is one `HTTP_TIMEOUT` interval (~15s) — **reserved against by `ENCODE_RESERVE`'s `HTTP_TIMEOUT` component specifically, cycle 7 correction** (`ENCODE_RESERVE = HTTP_TIMEOUT + CPU_PHASE_BUDGET`, so the drip reservation and the CPU-phase allowance no longer compete for the same headroom, unlike the prior revision's independently-chosen `ENCODE_RESERVE`: in a drip scenario the network phase can legitimately run to `network_budget + HTTP_TIMEOUT = 160s`, leaving exactly `CPU_PHASE_BUDGET = 20s` for the CPU phase — the figure it was actually sized against). T-16's gate 3 now checks `p95(CPU phase) ≤ CPU_PHASE_BUDGET` directly — see T-16.

The **pre-body phase** (connect, TLS handshake, status-line and header read) is a different story, and cycle 4 measured it empirically rather than estimating it: a mock server dripping headers one line at a time, each just under `HTTP_TIMEOUT`, drove the pre-body phase to `7.5 × HTTP_TIMEOUT` with no individual `recv` ever timing out — `http.client`'s own `_MAXHEADERS = 100` line cap means the theoretical worst case is far higher still, bounded only by however many blocking reads the header exchange takes, not by any single constant. Cycle 3's claim that this residual was "≈`HTTP_TIMEOUT`, absorbed by the `66.25s` margin" was wrong in **both** magnitude (it isn't one `HTTP_TIMEOUT`, it's `k × HTTP_TIMEOUT` for an unbounded-in-theory `k`) and in kind (the "margin" is nominal-case slack that has already been *spent* by the time a slow-drip scenario is underway — the actual reserve available against it is `ENCODE_RESERVE`, not the margin).

**This gap is accepted, not because the numbers work out, but because closing it would require a mechanism this plan deliberately does not build for v1, and because the actual threat model doesn't call for it.** A hard per-operation preemption (a `threading.Timer`-driven `socket.shutdown()` that unblocks a stalled `recv` from another thread) would bound the pre-body phase exactly — but that behavior is platform-specific and unverified across the 3.9/3.13 CI matrix, and building it is out of scope for a personal-use, stdio-only v1 talking to a fixed, TLS-verified, allowlisted host (`{www.youtube.com, youtubei.googleapis.com}`, confirmed by T-P3 — no `*.googlevideo.com` host is actually used for caption delivery in this plugin's scope). Producing an adversarial multi-minute header drip against this connection requires either compromising Google's own CDN infrastructure or a machine-in-the-middle capable of defeating TLS certificate verification — both already outside every threat this plugin defends against (the entire point of `ssl.create_default_context()` with verification on is to rule out the second). **AC-20's "within `DEADLINE + 1s`" bound is therefore scoped to the modeled case** (every blocking operation completes within its own socket timeout, the body-read loop's wall-clock check is what closes the loop) **and explicitly does not cover a fully adversarial pre-body drip** — stated here as a scope boundary, not a silently-accepted defect, since claiming otherwise (as the prior revision did) is worse than an honest gap. Revisit with the `threading.Timer` mechanism only if this plugin is ever exposed to an untrusted or attacker-reachable upstream host, which is a different threat model than v1's.

**CPU-phase budget (`CPU_PHASE_BUDGET = 20s`, one component of `ENCODE_RESERVE = 35s`)**: `formats.encode`/`count_pages_to` and the provider's decode steps (watch-page parse, player parse, timedtext parse, per-segment sanitize) each check `deadline.expired()` at intervals during their work, stride pinned as `DEADLINE_CHECK_STRIDE = 1000` segments (bounding this check's own overshoot to roughly `1000` segments' processing time, well under a second) — an abort here raises `DeadlineExpired`, uniformly translated (see below) into `status: "transport_error"`. `20s` is sized against the worst realistic CPU-phase invocation cycle 3 identified, not the 3-hour-fixture typical case cycle 2's version measured: the last page of a `MAX_PAGES = 20` read replays `count_pages_to` over up to `19 × MAX_PAGE_CHARS = 950,000` characters on top of a full `MAX_SEGMENTS = 100,000`-segment decode, sanitize, and final-page encode. T-P3 now measures this worst-case shape directly and T-16 gates on it (see Risks & Mitigations).

## Technical Approach

### Module layout and dependency direction

```
server.py ──► composition.py ──► providers/innertube.py ──► net/client.py
    │                                       │ (same-package edge)
    │                                       └──► providers/base.py, providers/video_ref.py
    │
    ├──► protocol/{registry,dispatch} ──► protocol/envelope.py, protocol/schemas.py
    │        (never tools/, never providers/innertube.py)
    │
    └──► tools/* (incl. tools/cursor.py) ──► formats/*, providers/base.py

domain/  ◄── net/, providers/base.py, providers/video_ref.py, providers/innertube.py,
             formats/, protocol/envelope.py, protocol/schemas.py, tools/*,
             composition.py, server.py   (every module above imports domain/ directly)
```

**Cycle 4 redrew this diagram** — the prior version showed `protocol/{dispatch,registry} → tools/*`, directly contradicting the table's "never `tools/`" clause on that same row (an inconsistency neither cycle 2 nor cycle 3 caught, since nobody cross-checked the picture against the table it illustrates), and omitted `composition.py`'s already-table-permitted `domain/` edge entirely (**cycle 8 correction**: `net/` was never actually one of `composition.py`'s permitted edges — the table grants it `domain/`, `providers/base.py`, `providers/innertube.py` only; a stray "and `net/`" claim in this sentence is removed here rather than restated). `tools/*` now sits where the table actually allows it — under `server.py` only.

**`tools/cursor.py`**, not `providers/cursor.py` (cycle 2 finding — its only consumer is `tools/`, which already imports `formats/` and `domain/`, so this placement needs **zero** new edges, unlike the previous `providers/` placement, which needed an undeclared `providers/ → formats/` edge just to reach `MAX_SEGMENTS`/`MAX_PAGES`).

**`ALLOWED_EDGES` — full, self-consistent table, cycle 3 revision.** Cycle 3 found two *new* instances of the exact gap cycle 2 thought it had closed: `providers/innertube.py`'s `MAX_SEGMENTS` enforcement (a cycle-2 fix) needs `formats/`, which its row didn't grant; and `protocol/envelope.py`'s track-object construction (also a cycle-2 fix) needs `formats.estimate_characters` and `providers.base.encode_track_id`, neither reachable from its `domain/`-only row. Both are fixed here — **not** by widening the cross-package edges (that would re-open the coupling cycle 2 closed), but by moving `MAX_SEGMENTS` to `domain/` (§ below) and by moving the two derived fields onto `TrackDescriptor` itself (§ next section) so both consumers already have what they need via edges they already hold. Cycle 3 also found the table was self-inconsistent in a second way: it spelled out same-package edges for `providers/` and `protocol/` but not for `tools/`/`formats/`, so under the "unlisted fails outright" rule an implementer had no way to know whether e.g. `formats/text.py → formats/__init__.py` needed a row. Fixed with one rule stated once instead of enumerated per package:

**A module may always import other modules within its own package** (e.g. `formats/text.py → formats/__init__.py`, `tools/get_transcript.py → tools/cursor.py`, `tools/{get_transcript,list_transcript_tracks}.py → tools/__init__.py`, `protocol/dispatch.py → protocol/registry.py`). The table below lists **only cross-package edges**; same-package entries from earlier revisions are removed as redundant now that the general rule states it once.

**Symbol-placement rule, cycle 7 — `hard-case-arbiter` diagnosis: a single stated rule closes the whole recurring class, generating the table from code does not.** The exact same defect shape — a module needs a symbol from a package it has no permitted edge to — recurred at five separate sites across cycles 2, 3, 4, 6, and 7 (`providers/cursor.py`'s original placement; `providers/innertube.py`'s `MAX_SEGMENTS`; `protocol/envelope.build()`'s track-construction fields; T-13a's `ProviderError` visibility, closed by `DomainFailure`; now `protocol/schemas.py`'s need for `formats.FORMATS`, introduced by cycle 6's own fix for a different finding). Each prior fix relocated one symbol without stating why, so the next symbol needing the same treatment wasn't recognized until review found it. One rule, stated once: **a symbol consumed by a package with no permitted edge to the symbol's current package lives in `domain/`.** (**Cycle 8 correction**: the rule as first stated in cycle 7 had a second disjunct — "consumed by more than one package" — architecture review found this over-broad and immediately falsified by the plan's own design: `parse_track_id`/`encode_track_id` (`providers/base.py`), the `TranscriptProvider`/`ProviderSession` port, and `MAX_PAGES` are each consumed by more than one package, but every consumer already has a permitted edge to the producer, so none of them needs relocating. The single remaining disjunct is the one doing the actual work — it explains and predicts all six historical instances with zero false positives, so it's the whole rule now, not half of it.) An earlier reviewer proposed generating `ALLOWED_EDGES` from the real import graph instead of maintaining it by hand — arbitrated and **rejected**: every one of the five instances was found in `tasks.md`'s prose, before any of the consuming code existed, so there was nothing to generate the table from at the point each gap actually needed catching; generating from code would also destroy the table's function as a design constraint (what's permitted, not what's observed) rather than close the recurrence. The mechanical backstop this plan already has — T-14's `test_real_import_graph_matches_allowed_edges`, checked against the real, fully-built import graph after Wave 3 — remains the right place to catch a *future* violation of the rule; the rule itself is what prevents the next symbol from needing a seventh ad hoc relocation.

`providers/innertube.py`'s row no longer lists `providers/base.py`/`providers/video_ref.py` (same-package, covered by the general rule) and no longer needs `formats/`, since `MAX_SEGMENTS` moves to `domain/` below — this closes cycle 3's Issue 1 with the edge count the row already had, exactly as the general rule and the constant's relocation were designed to do together. **One exception to the same-package rule, cycle 4 finding**: `providers/base.py` and `providers/video_ref.py` may **not** import `providers/innertube.py` — the general same-package rule accidentally legalized the abstraction (`providers/base.py`'s `TranscriptProvider`/`ProviderSession` ABCs) importing its own concrete implementation, the one dependency direction `composition.py` exists as a separate wiring layer specifically to avoid (AC-23/AC-24). Enforced by a dedicated self-test, since the general rule can't express a same-package negative case.

**A module not listed here fails the test outright** — the AST check (T-3) treats an unlisted module as a hard failure, never a silent pass. This same test also enforces two further boundaries: only `net/client.py` may import `urllib.request`, `urllib.error`, `http.client`, `socket`, `ssl`, `ftplib`, `asyncio`, `ctypes`, `xmlrpc.client`, `smtplib`, `webbrowser`, or `http.server` (list expanded in cycle 5 — the original six omitted several other stdlib modules with equivalent egress or dynamic-code capability); `importlib` is banned **everywhere**, including `net/client.py` (cycle 3 had granted it to `net/client.py` specifically, i.e. exactly the module where a dynamic-import-based egress bypass would be most dangerous, for a capability nothing in this plan ever needs there); and only `net/client.py` (specifically its `parse_xml_guarded` function) may import anything under `xml.*`. `__import__` is checked **separately**, in `test_source_policy.py`, as an AST walk for `Name(id="__import__")` nodes — cycle 5 finding: `__import__` is a builtin function call, never an `Import`/`ImportFrom` AST node, so a prior version of this check that claimed to ban it "everywhere" alongside `importlib` via the same Import-node scan was vacuously green by construction, since that scan structurally cannot see it. For every `ImportFrom` node, the check tests **both** `node.module` and `f"{node.module}.{alias.name}"` per imported name (checking `node.module` alone lets `from urllib import request` and `from http import client` through undetected, since neither string equals `"urllib.request"`/`"http.client"`; this was a real gap, not a contrived one — it is the natural way to write the import). AC-14's zero-pip-dependency check now compares against **two static, committed lists**, one per CI matrix leg — `stdlib_names_3_9.json` and `stdlib_names_3_13.json`, **each generated on that exact interpreter version**, never computed at test time (cycle 5 correction of cycle 4's own fix: "generated once from a 3.10+ interpreter's `sys.stdlib_module_names`" was itself wrong, verified empirically — the 3.9 and 3.10+ stdlib sets differ by over 20 module names in both directions, e.g. `distutils`/`smtpd`/`crypt` exist only pre-3.10 and `tomllib` only from 3.11, so a single list generated the cycle-4 way misclassifies real modules on whichever leg it wasn't generated for; `sys.stdlib_module_names` doesn't exist before 3.10 at all, so the 3.9 list needs a different generation method run on an actual 3.9 interpreter). The `sysconfig.get_paths()["stdlib"]` fallback cycle 3 added for the pre-3.10 leg is dropped entirely — verified empirically to pass every pip package on the standard layout `actions/setup-python` actually produces (`purelib`/`site-packages` nests inside `stdlib` there), and separately to crash on builtins like `sys`/`time` that have no `__file__` at all. A **separate** file, `test_source_policy.py`, owns everything that is a source-text pattern rather than an import-graph fact (TLS-bypass tokens, file-write/exec-primitive bans, the `__import__` AST-Name check, and the `urllib.request`/`urllib.error` attribute-access ban described next).

**The AST/text-ban mechanism is a regression guard, not a closed security boundary — stated explicitly as such, cycle 4 finding.** Cycle 3's bare-`urllib`-outside-`net/client.py` ban and its `from urllib.parse import urlsplit` mandate were empirically confirmed bypassable a second time: any module holding a reference reachable from `sys.modules` (e.g. via `import sys`, itself unrestricted, since restricting `sys` would be absurd) can reach `sys.modules["urllib.request"]` once `net/client.py` has imported it anywhere in the process — zero AST import node, zero banned source-text literal, in the bypassing module. No purely static, single-process-Python check closes this; the load-bearing guarantee that egress stays inside `net/client.py` is code review of that one file, same as it always was. The AST check and `test_source_policy.py`'s text bans are valuable as cheap, automatic **hygiene** — they catch accidental or careless violations immediately, in CI, before a reviewer ever looks — but this plan no longer describes them as "closing" the bypass, since claiming a mechanism closes something it cannot was exactly cycle 3's own overclaim, caught by cycle 4 the same way cycle 3 caught cycle 2's.

**The cross-package edge self-check moves from T-3 to T-14, cycle 4 finding.** Cycle 3 added it to T-3 as "every constant named in a task's `interface: consumes` line resolves to a permitted module" — but at T-3, the only thing to check against is `tasks.md`'s own prose, before any of the consuming code exists; a test built that way is vacuous by construction (green from creation, and green forever if the prose wording simply drifts from what gets built). T-14 runs after Wave 3, once the full module tree is built, and instead walks the **real** import graph: for every module under `plugin/server/**`, every imported symbol is resolved (following re-exports) to the module that actually defines it, and checked against that module's `ALLOWED_EDGES` permissions — the same property cycle 3 wanted, checked against code instead of documentation, which is what makes it capable of catching a live regression rather than only a documentation typo.

**The AST mechanism itself, hardened against cycle 3's four confirmed bypasses** (all four verified by executing code against the mechanism as previously specified):
1. **Attribute-access bypass** — `providers/video_ref.py` legitimately does `import urllib.parse` (for `urlsplit`); once `net/client.py` has done `import urllib.request` anywhere in the process, `urllib.request` becomes a live attribute reachable from any module holding a reference to the `urllib` package, with zero `ast.Import` node for `urllib.request` in the bypassing module. **Mitigated, not closed**, by mandating the `from urllib.parse import urlsplit` form (never bare `import urllib` or `import urllib.parse`) everywhere outside `net/client.py`, plus a `test_source_policy.py` text-ban on the literal patterns `urllib\.request\.`/`urllib\.error\.` outside `net/client.py` as defense in depth (the AST check alone cannot distinguish "imported `urllib.parse`" from "will later touch `urllib.request` via the shared package object") — cycle 5 empirically confirmed this specific mandate does not close the underlying class either: any module holding a reference reachable via `sys.modules` (trivially, via an unrestricted `import sys`) can still reach `urllib.request` once `net/client.py` has imported it anywhere in the process, with zero banned import or literal in the bypassing module. This and the other static checks in this section are consistently hygiene/regression guards (see the paragraph below), not closed boundaries — restated here rather than only in one place, since claiming closure inconsistently across otherwise-identical mechanisms is exactly the class of overclaim cycle 4 and cycle 5 both had to correct once already.
2. **`tree.body` vs. `ast.walk`** — a function-level or conditionally-nested import is invisible to a `tree.body`-only scan. T-3's acceptance now states the check walks `ast.walk(tree)`, with a self-test containing a function-nested banned import the check must still catch.
3. **Relative imports** — `from . import domain` yields `ImportFrom(module=None, level=1)`; a naive `node.module.startswith(...)` raises `AttributeError`. T-3's acceptance now states relative imports are resolved to an absolute dotted name from the file's own package path before comparison, with an explicit `node.module is None` branch and a self-test on `from . import x`.
4. **`importlib`** — added to the `net/client.py`-only restricted list above.

### Provider port — session-scoped (unchanged design from cycle 1, tightened after cycle 2)

```python
class TranscriptProvider(ABC):
    def normalize_video_ref(self, value: str) -> Optional[VideoId]: ...
    def open(self, video_id: VideoId, deadline: Deadline) -> "ProviderSession": ...

class ProviderSession(ABC):
    listing: TrackListing  # tracks may be an empty tuple — see the no_transcript redesign below
    def fetch(self, track: TrackDescriptor, deadline: Deadline) -> Transcript: ...  # raises UpstreamChanged if track is not
                                                                                      # (by identity/equality) a member of self.listing.tracks
```

**`fetch()` takes its own `deadline` parameter** (cycle 3 finding — the prior signature, `fetch(track)`, gave the session no declared way to receive a deadline for the timedtext leg's fetch-and-decode, which T-10 requires checking between the watch-page parse, player parse, and timedtext decode steps; the only way to satisfy that without a stated contract was for the session to silently retain the `Deadline` passed to `open()`, an unstated cross-call lifetime that mirrors the exact "unowned lifecycle" defect cycle 2 flagged one level up at T-13a/T-13b). Matching `net.fetch()`'s own shape (`deadline` as a required keyword there too), this makes "one invocation, one deadline, passed explicitly at each call that needs it" enforceable by the caller in `tools/` rather than implicit in the session. `FakeSession` in T-3 takes the same signature so T-11/T-12 exercise the real shape.

`open()` performs the 2-step resolution and returns a session holding the parsed player-response context as its own attribute — never on `TranscriptProvider` itself. `test_provider_holds_no_per_video_state` (T-10, cycle 2 finding) makes this a falsifiable property, not prose: it snapshots `vars(provider)` before and after two `open()` calls for different videos and asserts equality.

**The two steps are not independent — step 2 depends on step 1's output, named explicitly here (hostile-implementer-walkthrough finding, post-cycle-9)**: step 1 (watch-page GET) extracts `INNERTUBE_API_KEY` embedded in the page; step 2 (player POST to `youtubei/v1/player`) cannot be attempted without that key — this is the mechanism `swarm-report/research/research-youtube-subtitles-plugin.md` empirically verified (47+ live calls: fetch the watch page, pull `INNERTUBE_API_KEY`, POST with `ANDROID`/`IOS` client context, never `WEB` — see that report's Evidence section for why `WEB` fails at an earlier barrier). If step 1's watch-page GET succeeds at the HTTP level but the page's embedded JSON (`ytInitialPlayerResponse` inside a `<script>` tag — see T-10) or the API key cannot be located structurally, that is `UpstreamChanged` and step 2 is never attempted — this is a different failure than either step's own JSON-parse or HTTP-transport failures, and needs its own fixture (a watch-page HTML body with no `ytInitialPlayerResponse` assignment at all, e.g. a consent-interstitial page).

**Correction, live-fix pass, 2026-08-03** (see `providers/innertube.py`'s own module docstring and `swarm-report/youtube-transcript-report-live-fix.md`): as of this date, `ANDROID`/`IOS` client context at step 2 (the player POST) is blocked by a device-attestation check added upstream — a real-world change, not a defect in the above research. Step 2 now uses `WEB` client context, together with a `signatureTimestamp` (`STS`) extracted from the same step-1 watch-page HTML (no new request), and this combination is empirically confirmed working. This does not contradict the research report's "`WEB` fails at an earlier barrier" finding: that finding was about a `WEB`-context *watch-page GET* (step 1), never tried with a `signatureTimestamp` at the *player POST* (step 2) — a distinct leg this fix never changes. Step 1 keeps sending `_USER_AGENT` as its own header regardless of `context.client.clientName`, which only appears in step 2's POST body.

**`NoTranscript` is no longer a raised exception** (cycle 2 finding — the prior design raised it from `open()`, which meant `session.listing` was never populated for a captionless video, and AC-1's "root-level `videoDurationSeconds`" therefore had no data source on that path, since a video's duration comes from `videoDetails` in the same player response, independent of whether it has captions). Instead, `open()` always succeeds for a playable video regardless of whether it has captions; `session.listing.tracks` is simply an empty tuple when there are none, and `session.listing.duration_seconds` is populated either way. `tools/list_transcript_tracks.py` and `tools/get_transcript.py` both check `if not session.listing.tracks: status = no_transcript` — the same layer that already resolves `language_unavailable`/`ok`, so this fits the existing "domain outcome resolved in `tools/`, not the provider" pattern rather than adding a new special case. The `ProviderError` hierarchy shrinks to 10 subclasses (`VideoNotFound`, `VideoUnavailable`, `AgeRestricted`, `RegionBlocked`, `LiveNotReady`, `RateLimited`, `BlockedByProvider`, `UpstreamChanged`, `TranscriptTooLarge`, `TransportError`).

**Cycle 3 found this redesign, while correct in its main line, silently dropped the spec's positive playability gate — a security-relevant regression, fixed here.** The spec's status table requires `no_transcript` be reached "only via the positive path: `playabilityStatus.status == "OK"` AND the `captions` key is absent or present-with-zero-tracks — explicit assertion, not a `.get()`-with-default chain". `open()`'s discrimination is restated here as that positive gate, not as a denylist on `ERROR` alone: **`open()` raises a `ProviderError` unless `playabilityStatus.status == "OK"`**; any other value — `ERROR`, `UNPLAYABLE`, `LOGIN_REQUIRED`, `AGE_CHECK_REQUIRED`, `CONTENT_CHECK_REQUIRED`, `LIVE_STREAM_OFFLINE`, or anything unrecognized — is mapped by the discriminator table below, defaulting to `VideoUnavailable` when no more specific subclass matches. Without this positive framing, the natural implementation is `if status == "ERROR": <map> else: <proceed>`, which reports `no_transcript, retryable: false` for a private, age-gated, or login-walled video — exactly the status-integrity failure AC-9/AC-7 exist to prevent, made reachable by this cycle's own redesign (previously the provider raised before ever producing a listing, so this path didn't exist).

**The discriminator table itself, named explicitly (hostile-implementer-walkthrough finding, post-cycle-9 — nine `multiexpert-review` cycles asserted this table exists without ever writing it down):**

| `playabilityStatus.status` / observed condition | maps to | evidence |
|---|---|---|
| `OK`, `captions` key present | proceed to captions-shape discrimination below | empirically confirmed, 6/6 full runs including a user-supplied video (`research-youtube-subtitles-plugin.md`) |
| `ERROR` / "unavailable", no `captions` key | `VideoNotFound` | empirically confirmed (research report) |
| `UNPLAYABLE` / "processing", no `captions` key | `LiveNotReady` | empirically confirmed (research report — live/in-processing videos) |
| `LOGIN_REQUIRED` | `AgeRestricted` if `reason` mentions age/sign-in-to-confirm-age, else `VideoUnavailable` | **not empirically observed — synthetic fixture** (see below) |
| `AGE_CHECK_REQUIRED`, `CONTENT_CHECK_REQUIRED` | `AgeRestricted` | **not empirically observed — synthetic fixture** |
| `UNPLAYABLE` with a region-block-shaped `reason` (e.g. containing "not available in your country") | `RegionBlocked` | **not empirically observed — synthetic fixture, `reason` string is best-effort from public knowledge of YouTube status values, not verified** |
| `LIVE_STREAM_OFFLINE` | `LiveNotReady` | **not empirically observed — synthetic fixture** |
| any unrecognized `status`/`reason` | `VideoUnavailable` (default) | design choice, not empirical |

The three empirically-confirmed rows are load-bearing and tested against real behavior. The synthetic rows exist because research explicitly could not trigger them in 47+ live calls across 5+ videos and 3 client contexts (`research-youtube-subtitles-plugin.md`'s "Known Unknowns") — this matches spec AC-17's own honest disclosure that these three statuses are fixture-only, not a gap introduced by planning. **Do not invent a more "precise-looking" `reason` string during implementation than what's written here** — if implementation-time testing (or the live canary, T-15, or a future user report) surfaces a real trigger, update the table then; a plausible-but-unverified string is not worth more confidence than an honestly-labeled placeholder.

**`blocked_by_provider`'s discriminator (HTTP 403 + a consent-wall body marker, or a bot-check `reason` string) is the same class of gap, more acute**: research found **zero** observed blocks across every call made (no `exp=xpe`/`exp=xpv` marker, no 403, on any client/video combination tried) — there is no empirical basis for the marker string at all, synthetic or otherwise. Implement the discriminator as an isolated, easily-updated function (a short list of candidate markers, not inlined into the main dispatch logic) specifically so it's cheap to correct once a real block is ever observed, rather than optimizing for correctness on day one against data that doesn't exist yet.

Separately, the `captions`-container shape itself now gets a three-way discrimination rather than defaulting to empty on any parse hiccup (cycle 3's second finding in this area — a genuinely absent `captions` key and a `captions` key with an unexpected shape were both silently collapsing to the same empty-tracks `no_transcript` result, masking the upstream-format-drift signal this plugin's `upstream_changed` status exists to surface): (a) `captions` key **absent** → empty tuple, `no_transcript` (legitimate — most videos have no captions); (b) `playerCaptionsTracklistRenderer` present with `captionTracks: []` → empty tuple, `no_transcript`; (c) `captions` key present but its expected sub-structure missing or of an unexpected type → raise `UpstreamChanged`, not a silent empty tuple.

### `ProviderError`/`DeadlineExpired` → `domain.ToolOutcome` translation (single owner, now covering both exception families)

`tools/__init__.py::outcome_from_error(exc: Union[ProviderError, DeadlineExpired]) -> ToolOutcome` is the **only** place either exception family becomes a `ToolOutcome`. Cycle 2 found `DeadlineExpired` (introduced by cycle 1's own fix threading the deadline into `formats/`) had no translation owner and no totality coverage — it is now folded into the same function and the same totality test (asserting every `ProviderError` subclass **and** `DeadlineExpired` map to a `Status` present in `STATUS_POLICY`, `DeadlineExpired` always to `transport_error`).

**`domain.DomainFailure(Exception)` — new common base, cycle 4 finding.** T-13a's acceptance requires `protocol/`'s dispatch layer to distinguish "a domain-modeled failure escaped a handler it shouldn't have" (a safety net, translated to a generic outcome) from "a genuine bug" (→ `-32603`) — but `protocol/`'s `ALLOWED_EDGES` row is `domain/` only, and `ProviderError` lives in `providers/base.py`. Cycle 3's design left this either unenforceable (the registry can't check exception identity without the forbidden edge) or contradicted the row (importing it anyway). Fixed by introducing `DomainFailure(Exception)` in `domain/`, with `ProviderError(DomainFailure)` (`providers/base.py`, T-3) and `DeadlineExpired(DomainFailure)` (`domain/`, T-2) both inheriting it — `protocol/` can now do `isinstance(exc, DomainFailure)` using only its already-permitted `domain/` edge. This is also, incidentally, the natural home for the "both exception families" language `outcome_from_error`'s signature already used informally — it is now a real, checkable type relationship (`Union[ProviderError, DeadlineExpired]` narrows to `DomainFailure` throughout).

### `net/`'s exception set gains one member (cycle 2 finding — the XML guard's own rejection was unmapped)

`MalformedUpstream(NetError)` — raised by `parse_xml_guarded()` when it catches its own DOCTYPE/entity-rejection handler firing, or `xml.parsers.expat.ExpatError` from genuinely malformed XML (truncated body, mismatched tags). `providers/innertube.py`'s `net`-exception → `ProviderError` table gains `MalformedUpstream → UpstreamChanged`. Without this, both failure modes previously escaped uncaught into `isError: true`, contradicting AC-10 and dropping AC-20's explicit "a rejection here also maps to `upstream_changed`".

**Cycle 3 finding: this mapping closed for `MalformedUpstream` specifically, by enumeration, but nothing makes the *next* `net/` exception's mapping mandatory.** T-10 gains a structural totality test mirroring T-3's `outcome_from_error` totality test: it iterates `NetError.__subclasses__()` recursively and asserts every one has a row in the provider's `net`-exception → `ProviderError` table, failing on any unmapped subclass rather than on an absent hand-written parametrize entry — the same defect class (an exception family that grows a new member with no test forcing its mapping) that produced the original `MalformedUpstream` gap. Two mappings implied elsewhere but never stated are pinned explicitly by this same table: `PolicyRejected → UpstreamChanged` (AC-19 — a host-allowlist rejection and a redirect both surface as `upstream_changed`) and `ResponseTooLarge → TranscriptTooLarge`.

**Cycle 3 also found the two JSON-parsing legs (watch-page and player-response) have no equivalent to the XML guard's error mapping.** Two of the three legs are JSON, not XML; nothing in the provider maps `json.JSONDecodeError` on a truncated or HTML-error body, or `KeyError`/`TypeError`/`IndexError` while walking `playerResponse["captions"]["playerCaptionsTracklistRenderer"]["captionTracks"]` or extracting `ytInitialPlayerResponse` from the watch page. Per the spec's status table, a structural-assertion failure maps to `upstream_changed` (`isError: false`); an uncaught `KeyError` instead produces `isError: true`, the same domain/bug misclassification this cycle's XML fix closed on the one leg that already had it. T-10 wraps every structural JSON decode step so these four exception types map to `UpstreamChanged`, with one fixture-backed test per case (truncated JSON body, an HTML consent page in place of JSON, a player response missing `videoDetails`, a response with `captionTracks` renamed) — distinct from the legitimate `captions`-key-absent path described above, which must remain a `no_transcript`, not an `UpstreamChanged`.

### XML guard, wired precisely (cycle 1's mechanism confirmed correct by cycle 2's empirical re-verification; this section closes the seams cycle 2 found around it)

`parse_xml_guarded(data: bytes) -> Element`, the only function this design intends to touch `xml.*` (AST-enforced as a hygiene/regression guard, per the reframing above — not a claim that no other code path could ever reach `xml.*` in a single-process Python program): raw `xml.parsers.expat.ParserCreate()`, `StartDoctypeDeclHandler`/`EntityDeclHandler`/`ExternalEntityRefHandler` all set to a function that raises a local sentinel exception, feeding an `xml.etree.ElementTree.TreeBuilder` via `StartElementHandler`/`EndElementHandler`/`CharacterDataHandler`; both the local sentinel and `expat.ExpatError` are caught at the function boundary and re-raised as `MalformedUpstream`. The requested timedtext payload is non-namespaced XML (`<timedtext format="3"><p t=".." d="..">text</p></timedtext>`, confirmed by the research spike) — `ParserCreate()`'s default (non-namespace-aware) tag handling is therefore correct as-is; a fixture-based test asserts the exact tag names produced, so a future format change that introduces namespaces is caught rather than silently returning an empty transcript.

### Outbound-fetch policy, wired precisely (cycle 1's mechanism confirmed correct by cycle 2's empirical re-verification; this section closes the seams cycle 2 found around it)

- **Scheme + host**: `host = urlsplit(url).hostname` (cycle 2 finding: pinning the exact accessor matters — `urlsplit("https:///x").hostname` is `None` while `.scheme` is still `"https"`, and a naive `host.endswith(...)` on `None` raises unmapped `AttributeError`); `if not host or not scheme_ok: raise PolicyRejected` before any comparison, `scheme != "https"` checked first.
- **Opener**: explicit `OpenerDirector()` + `HTTPSHandler(context=...)` + the no-redirect handler + `HTTPErrorProcessor`/`HTTPDefaultErrorHandler` + `ProxyHandler({})` — never `build_opener()`'s default set (empirically confirmed by cycle 2 to fetch `file:`/`data:` otherwise).
- **Redirects**: cycle 2 found the prior draft's "raises `PolicyRejected` via a `redirect_request`-returns-`None` handler" was imprecise to the point of being wrong — that handler prevents the redirect from being *followed*, but the caller actually receives `urllib.error.HTTPError` with `.code` in the 3xx range (empirically confirmed, including 305, which `HTTPRedirectHandler` never special-cases). `fetch()` now explicitly inspects `HTTPError.code`: `300 <= code < 400` → `PolicyRejected`, checked **before** the 429 and 5xx branches so a redirect can never be misread as a rate-limit or transport failure.
- **TLS bypass tokens** (`test_source_policy.py`, T-6a): `_create_unverified_context`, `CERT_NONE`, `check_hostname\s*=\s*False`, **and** (cycle 2 finding) `ssl.SSLContext(` and `_create_default_https_context` — a bare `ssl.SSLContext()` defaults to unverified without tripping any of the first three tokens.
- **Outbound headers, split ownership (cycle 8, corrected cycle 9)**: `net.fetch()` sends `Accept-Encoding: gzip` unconditionally on every request — the one header AC-20 actually mandates at the `net/` layer. `User-Agent` is **not** one of `net/client.py`'s responsibilities: cycle 8's fix had `net/client.py` (Wave 0/1, `ALLOWED_EDGES` row `domain/`-only) consume a `USER_AGENT` constant from `server.py` (Wave 3) — an edge that cannot exist and a wave order that cannot resolve, on top of directly contradicting the spec's own already-recorded decision that the outbound UA to YouTube is the ANDROID/IOS client's own conventional UA string, not this plugin's protocol-identity `USER_AGENT` constant (AC-12, which identifies the MCP server to its *caller*, not the plugin's HTTP identity to YouTube). Fixed, cycle 9: `providers/innertube.py` (T-10) — which already builds the ANDROID/IOS client context for each leg — sets `User-Agent` on the `headers` dict it passes into `net.fetch(..., headers=...)`. **Merge direction corrected by tasks.md's narrow-check fix Y-5 (T-6b implementation, not reflected in this sentence until now)**: `fetch()` merges `BASE_HEADERS` (`Accept-Encoding: gzip`) **on top of** caller-supplied `headers`, i.e. the base set wins any collision, not the caller — the prior wording here ("caller headers taking precedence") was cycle 9's first draft, which let a caller send `Accept-Encoding: identity` and silently defeat AC-20's "unconditionally"; the base set exists precisely to be non-overridable. Both sides' keys are normalized via `.title()` before merging (Y-7) so the merge's stated precedence is the actual precedence, not an accident of casing.

### Untrusted-content boundary, redesigned from a fixed sentinel to a per-call random value (cycle 6 escalation — see spec Decisions Made for the full history this section summarizes)

**This mechanism went through cycles 2 through 6 of `multiexpert-review` as a fixed-constant "sentinel" (`CONTENT_SENTINEL`) that every text-transform touching transcript content had to correctly avoid reconstructing — and a genuine, often execution-verified defect was found in a *different* transform at that obligation, every single cycle**: a bare `assert` stripped by `-O` (cycle 2); a wrap-vs-neutralize ordering contradiction and an unfalsifiable cross-segment test (cycle 3); non-idempotent single-pass removal and an unpinned literal (cycle 4); a worse capped-loop failure mode (`ValueError` reaching `-32603`) plus a removal step that could forge a `-->` cue-boundary token via interaction with a sibling transform (cycle 5); the *sibling* transform (AC-21's `-->`→`->` collapse) turning out to have the identical non-idempotency defect independently, reachable without the sentinel at all (cycle 6). Six cycles fixing the *day's instance* of the same structural problem is the signal that the problem is structural, not a sequence of coincidences — this revision changes the mechanism instead of patching the sixth instance.

**The redesign, decided with the user directly after cycle 6's escalation, and now reflected in the spec (AC-15/AC-21, see `docs/specs/2026-08-01-youtube-transcript.md`'s Decisions Made):** the boundary delimiter is generated fresh, per tool call, from a cryptographically random source — `domain.generate_content_boundary() -> str`, returning `f"<<<UNTRUSTED_CONTENT_{secrets.token_hex(16)}>>>"` (128 bits of entropy) — called once inside `protocol/envelope.build()` for that response. Since the caption text being wrapped was authored on YouTube before this specific tool call (and therefore before this specific boundary value exists), an attacker cannot predict or embed a matching forged copy of it. **This closes the forgery concern by construction, not by scrubbing** — there is nothing left for `sanitize_text` or `build()` to search for or remove, so neither does: `sanitize_text` (T-2) goes back to being exactly what its name says (control-character stripping, one `str.translate`/regex pass, nothing else), and `build()` simply wraps the assembled text between two copies of the fresh boundary value with no neutralization step of any kind.

**AC-15 reopened a second time, cycle 7 — `hard-case-arbiter` diagnosis: predictability was closed, verifiability was not.** The redesign above closes *predictability* — an attacker cannot forge a copy of a boundary value that doesn't exist yet at authoring time. But cycle 7's review found the very next gap in the same mechanism: a consumer (the model reading the response) that never learns the boundary's actual value cannot distinguish a real occurrence from a well-formed forged one embedded in caption text — confirmed by execution, a forged `<<<UNTRUSTED_CONTENT_...>>>`-shaped token plus a forged trailing epilogue is accepted by the T-7 test that only asserts "exactly two occurrences." Arbitrated as a second, independent structural gap in AC-15 (not a seventh reactive patch): `contentNotice` is no longer a static string but a function of the call's actual boundary value — `content_notice(boundary: str) -> str` (T-7).

**Cycle 8 found the cycle-7 fix's own counting arithmetic broken: `content_notice()` quotes the boundary value literally, so the value appears 3 times in a naively-serialized response (once inside the notice, twice as the wrap), not 2 — breaking both T-7's "exactly two occurrences" acceptance and AC-26's reference-parser algorithm, which read literally identifies the in-notice occurrence as the "first occurrence" and leaves the transcript itself outside the recognized region.** Cycle 8 fixed this by making `contentNotice` a separate key in the Python dict `build()` returns, distinct from the wrapped-transcript key — but cycle 9 (security, then confirmed independently by architecture, then `hard-case-arbiter`'s second arbitration) found this dict-level separation has no carrier once the response actually crosses the wire: this repo's own MCP pattern (confirmed against `plugins/maven-mcp/plugin/server/server.py:11510`) serializes the entire result dict with one `json.dumps()` into the single text block `content[0].text` of the tool's `CallToolResult` — there are no separate MCP-level fields for `build()`'s dict keys to land in, and `outputSchema`/`structuredContent` are explicitly not used for `get_transcript` (see below). Two dict keys therefore still concatenate into one serialized string on the wire, exactly as they did before cycle 8's fix, and the original 3-vs-2 counting problem was never actually closed — only pushed past `build()`'s own return value, where cycle 8's tests could no longer see it.

**Fixed correctly, cycle 9 — pin the actual wire carrier and give AC-26's parser two explicit steps, not one substring search.** `build()`'s separate `contentNotice`/wrapped-transcript dict keys are the right design and are unchanged; what cycle 9 adds is naming the carrier those keys travel over and matching the verification algorithm to it. `protocol/registry.py`'s `Registry.call()` (T-13a) serializes `build()`'s full result dict with one `json.dumps()` into `content[0].text` — this is the single, explicit, named carrier, stated as such rather than left implicit. `outputSchema` is **not declared** for `get_transcript` in v1 (decided cycle 8, unchanged — the simplest choice, and it removes any risk of the wrapped text being duplicated into a second, unwrapped `structuredContent` copy).

The response layout is pinned at the dict level (unchanged from cycle 8): the wrapped transcript text lives under a literal key named **`transcript`** (named explicitly by the post-cycle-9 narrow check — previously only described as "the wrapped-transcript key," which left `FIELDS_BY_STATUS[Status.ok]` unfrozen and the name itself undeclared anywhere a reader or an implementer could check against); `contentNotice` is present as its own key whenever `transcript` is; `transcript`'s value contains the boundary exactly twice with the caption text between the two occurrences, and no other dict value repeats that exact value (a `test_boundary_appears_in_exactly_two_dict_values` recursive scan now checks this directly, T-7 — previously stated in prose only). Spec AC-26 (revised cycle 9) is the class-closing verification criterion, now matched to the real carrier: a reference deterministic parser, given the raw bytes of `content[0].text`, **first** `json.loads()`s them to recover the structured dict, **then** extracts the boundary value from the parsed dict's `contentNotice` key and searches **only the parsed dict's `transcript` key** for exactly two occurrences of that value, returning the text between them as the untrusted region — zero, one, or three-or-more occurrences within that one key is an error, not a best-effort guess (that the raw, pre-`json.loads()` text contains the value a third time, inside the JSON-encoded `contentNotice` string, is expected and not itself checked by this parser — it operates on the parsed structure, never on the raw serialized bytes as an undifferentiated blob). Tested against three adversarial fixtures: (a) a forged boundary-shaped token in the caption text, (b) a forged `content_notice`-shaped string naming a fake value embedded in the caption text, (c) caption text containing the literal prefix `<<<UNTRUSTED_CONTENT_` without a valid 32-hex-digit suffix and closing bracket (a partial-prefix collision) — the parser must not be misled by any of the three, since it matches on the complete, exact value named in the parsed `contentNotice`, never a prefix or substring, and never on raw bytes before parsing. This is what makes a *future* regression in this mechanism fail a direct test against the actual wire format instead of only a narrower proxy (an in-memory dict, or a raw substring count) that let two successive gaps through undetected. See spec Decisions Made for the full arbitration record.

**Post-cycle-9 narrow check (security-expert, opus, scoped to only the four cycle-9 fix areas — not a tenth full panel cycle) found the design in this section correct but its own verification incomplete: T-7's unit test for the reference parser built its `json.loads()` input via a `json.dumps()` call made inside the test itself, not the actual bytes `protocol/dispatch.py` sends.** That is still a reconstruction, one step closer to the wire than cycle 8's pre-serialization dict but not the wire itself — a divergence in the real serialization step (different `json.dumps` options, an extra wrapping layer) would leave the T-7 unit test green while the real response failed. **Closed by moving AC-26's actual closing test to T-14**, where it dispatches all three adversarial fixtures through the real `handle_message` stack and feeds the reference parser `response["result"]["content"][0]["text"]` verbatim; T-7's version remains as fast unit-level coverage of the parser algorithm, no longer claimed as the sole test that satisfies AC-26. The narrow check's other findings in this section were correctness-of-language, not design changes: `Registry.call()`'s serialization step (T-13a) now also states explicitly that it does not copy the reference implementation's second branch (a `str(exception)`-carrying, `isError: true` fallback for arbitrary exceptions) — excluded on the same two grounds this whole mechanism already rests on, AC-15's ban on `str(exception)` reaching a caller and AC-10's `isError: false`-everywhere `STATUS_POLICY`.

**AC-21's cue-injection-neutralization (`-->`→`->`, blank-line collapse) survives, but demoted from a security requirement to a format-correctness one** (spec Decisions Made) — the whole transcript is already wrapped in an unforgeable random boundary and marked untrusted, so this transform no longer needs to be adversarially idempotent; a residual imperfection here affects only how faithfully the interior SRT/VTT structure round-trips, not whether untrusted content could be mistaken for trusted content. It is still implemented correctly (cheaply): a longest-match regex (`re.sub(r"-{2,}>", "->", text)`) closes the one real defect cycle 6 found in it (`"--->".replace("-->","->")` reconstructs `"-->"` under naive single-token replace) — but this is ordinary correctness work, not a security-critical proof, and no longer blocks AC-15/AC-10 compliance if it has an edge case. (Cycle 7 fix: this line and its test fixture were previously written with the HTML entity `&gt;` in place of the literal `>` character, matching nothing in real `-->` text and letting the paired test pass vacuously — see `tasks.md` T-5 for the full note.)

**What this removes outright, not patches**: the pinned `CONTENT_SENTINEL` literal and its choice of excluded substrings; the stack-based single-pass removal algorithm at both layers; the fixed inert placeholder in `build()`; the capped fixed-point loop and its `ValueError`; every positive-control/nested-splice/transform-synthesis test built around any of the above; the "hygiene not boundary" framing this specific mechanism needed (it never applied to the AST/import-boundary checks, which are unaffected). None of these are "fixed a seventh time" — they no longer exist in the design.

### Response payload — allowlist enforcement now covers nested structure (cycle 2 finding — the previous filter was top-level-only, so a `list_transcript_tracks` response's per-track objects, built ad hoc in `tools/`, could carry an unvetted field through untouched)

`protocol/envelope.py`'s `build()` constructs the `tracks` array itself from `TrackDescriptor` fields explicitly (`{"trackId": ..., "languageCode": ..., "languageName": ..., "kind": ..., "estimatedCharacters": ...}`, a fixed literal shape) rather than passing through a dict `tools/list_transcript_tracks.py` assembled — so there is no nested object whose key set isn't independently pinned. Dropped top-level payload keys are logged (DEBUG) by name only, never by value, avoiding a second leak path alongside the one closed in `net/client.py`.

**Cycle 3 finding, fixed then re-broken then fixed again here: `build()` as stated could not actually construct that literal shape, and the first fix introduced a contract error of its own.** Two of the five keys are not `TrackDescriptor` fields and were not reachable from `protocol/envelope.py`'s `ALLOWED_EDGES` row (`domain/` only): `estimatedCharacters` is derived by `formats.estimate_characters` (`formats/` not in envelope's row) and `trackId` is produced by `encode_track_id` in `providers/base.py` (also not in envelope's row) — while T-11 explicitly computes `estimated_characters` in the tools layer, meaning it could only reach `build()` through the payload, which is exactly what the "construct, don't pass through" fix says `build()` must not do. Cycle 3 resolved this by giving `TrackDescriptor` two derived fields, `track_id: str` and `estimated_characters: int` — but AC-1 defines `estimatedCharacters` as an **object**, `{text, srt, vtt}` (three independently derived figures — text-format character count, and the srt/vtt figures each `text × CUE_OVERHEAD_FACTOR`), not the scalar cycle 3's fix declared; cycle 4 caught this contract mismatch, introduced by the fix itself, empirically against the spec text.

**Cycle 4's fix, split ownership as well as fixed the type**: `TrackDescriptor.estimated_characters` is `Optional[Mapping[str, int]]` with keys `{"text", "srt", "vtt"}`, `None` until populated. `track_id` stays populated by the provider at construction time via `encode_track_id` (`providers/base.py`'s own function — only its string *output* travels onto the domain object, so `providers/innertube.py`'s existing `domain/`-only edge for this purpose is unaffected). `estimated_characters` is populated **exclusively** by `tools/list_transcript_tracks.py` (T-11), which already has the `formats/` edge that computation needs: it builds new, response-only `TrackDescriptor` copies carrying the computed mapping, alongside (never replacing) the original provider-returned descriptors in `session.listing.tracks`, which `fetch()`'s "member of `self.listing.tracks`" precondition still checks against — a distinction that matters because `list_transcript_tracks` never calls `fetch()` at all, so there is no code path where an enriched copy could accidentally be presented where an original is required. `build()` then genuinely constructs the fixed-shape `tracks` array from these fields alone, with zero new edges — the property both cycle 3 and cycle 4's fixes were reaching for.

**Cycle 4 also found `resolvedTrack` (AC-5) and `availableLanguages` (AC-3) — both response fields the spec requires — had no owning task at all.** `resolvedTrack: {languageCode, kind, sourceLanguageCode}` names which track a successful `get_transcript` actually resolved to; `sourceLanguageCode` is always `None` in v1 since `kind` is never `"translated"` (that value is reserved schema space for the not-yet-implemented Phase 4 translation feature). Fixed the same way as `tracks`: `tools/get_transcript.py` (T-12) puts the resolved `TrackDescriptor` into its outcome's payload as `resolved_track`, and `envelope.build()` constructs the wire-shape `resolvedTrack` object from its fields directly — the same "construct from a domain object, don't pass through a tools-assembled dict" pattern, applied to the one nested object the original allowlist fix's own reasoning should have already covered. `availableLanguages: string[]` (capped at 50, AC-1's shared cap) is now part of `T-7`'s `FIELDS_BY_STATUS[language_unavailable]`, and `T-12` populates it from `session.listing.tracks`' `languageCode`s when `select_track` finds no match.

### `MAX_SEGMENTS` moved to `domain/` (cycle 3 finding: `providers/innertube.py` needs it and its row does not grant `formats/`)

`MAX_SEGMENTS = 100_000` moves from `formats/__init__.py` to `domain/__init__.py` (T-2, not T-3). It is a bound on `Transcript`, a `domain/` object, not on output formatting — and it now has three consumers in three different packages (`formats/` for `count_pages_to`'s ceiling, `tools/cursor.py` for cursor `segmentIndex` validation, `providers/innertube.py` for decode-time enforcement), which is precisely the signal that it belongs in the package everything already imports rather than in a sideways `providers/ → formats/` edge that would re-open the coupling cycle 2 closed when it moved `cursor.py` out of `providers/` for the same reason. `formats/__init__.py` re-derives nothing — it imports `MAX_SEGMENTS` from `domain/` alongside `Transcript`/`Segment`, which it already does. AC-11's literal "`formats/__init__.py`" placement is now a documented spec/plan divergence (see Verification & Sources).

**`FORMATS` moves the same way, cycle 7 — the symbol-placement rule applied, not a new decision.** `FORMATS: FrozenSet[str] = frozenset({"text", "srt", "vtt"})` (AC-4's format enum) moves from `formats/__init__.py` to `domain/__init__.py` (T-2, not T-5): it is consumed by `protocol/schemas.py` (T-7's `TOOL_SCHEMAS`), `tools/cursor.py` (T-8), `tools/get_transcript.py` (T-12), and `formats/`'s own `encode()` (T-5) — four consumers in three packages. **Corrected justification, cycle 8**: `tools/`'s `ALLOWED_EDGES` row already grants it `formats/`, so it needs no relocation to reach `FORMATS` there — the sole consumer without a permitted edge is `protocol/schemas.py`, and that alone is sufficient under the corrected, single-disjunct placement rule above. `formats/__init__.py` re-exports it from `domain/`, exactly as already done for `MAX_SEGMENTS`.

**`HTTP_TIMEOUT` moves the same way, cycle 8 — the placement rule's own worked example (`ENCODE_RESERVE = HTTP_TIMEOUT + CPU_PHASE_BUDGET`) violated it in the same revision that introduced it.** `ENCODE_RESERVE` is derived in `domain/` (§ above), but `HTTP_TIMEOUT` lived in `net/client.py` and `domain/`'s `ALLOWED_EDGES` row is `nothing` — the derivation as stated was not constructible in code. `HTTP_TIMEOUT = 15` moves to `domain/__init__.py` (T-2, not T-3); `net/client.py` re-exports it from `domain/` for the socket-level `fetch()` call sites that need it directly, the same re-export pattern already used for `MAX_SEGMENTS`/`FORMATS`. This is the placement rule's own second consumer-without-an-edge case (`domain/` itself, needing a symbol from `net/`, which it can never have a permitted edge to under any revision of the rule), caught by architecture review the cycle after the rule was stated — recorded as a divergence from spec AC-20's literal "all defined in `net/client.py`" placement, alongside the five other divergences already tracked (see Verification & Sources).

### URL/secret redaction now covers both layers (cycle 2 finding — the redacting-logger fix from cycle 1 only touched `net/client.py`, but the object holding a signed `baseUrl` is `InnertubeSession`, in `providers/`)

The redaction helper (`urlsplit(u)._replace(query="").geturl()` before any log call) moves to `domain/` (both `net/` and `providers/` already import it) and is mandated in both T-6b's and T-10's acceptance.

### Cursor — reverted to 5 fields (cycle 2 finding — `pageOrdinal` was mathematically unreachable: the server never emits a cursor with `pageOrdinal >= MAX_PAGES`, since it returns the truncation response at exactly that boundary instead, so the "fast-reject" branch had no legitimate input that could ever trigger it, while a forger gains nothing from a low value either, since the authoritative derived check still runs — the field cost a wire-format change, a validation rule, and a task, for zero measurable benefit, and it also directly contradicted T-8's own "exactly five keys" acceptance line)

`CursorFields(video_id, track_id, format, include_timestamps, segment_index)` — back to the original five, matching AC-11's literal enumeration. The `MAX_PAGES` ceiling is still enforced exactly as before cycle 1's fast-reject attempt: derived, via `formats.count_pages_to` replaying from `segmentIndex = 0`, no stored counter — a request past the ceiling does still pay a full fetch + decode before being told so, which is an accepted, disclosed cost (see Decisions Made), not a defect this revision tries to remove a second time.

### `MAX_SEGMENTS` enforced where segments are actually created (cycle 2 finding — it was previously checked only against cursor input and against the real count in phase 2, never during decode itself, so a response within the byte cap could still decode to an unbounded segment count)

`providers/innertube.py`'s decode loop raises `TranscriptTooLarge` the instant segment count would exceed `MAX_SEGMENTS`, rather than materializing an unbounded tuple first.
